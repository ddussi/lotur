## 1. 목표와 완료의 의미

Review Tunnel을 신뢰 관계가 있는 소규모 팀이 자체 운영할 수 있는 오픈소스 알파로 준비한다. 처음 접한 개발자가 문서만 따라 로컬에서 리뷰 흐름을 체험하고, 검증된 배포물을 설치하며, 기존 데이터를 보존하면서 업데이트할 수 있어야 한다.

준비 완료와 공개 완료를 구분한다. 로컬 구현이나 CI 통과만으로 전체 목표를 완료 처리하지 않는다.

| 단계 | 완료 조건 |
| --- | --- |
| 공개 후보 준비 완료 | 아래 P1–P6의 필수 검증이 통과하고, 공개할 커밋·배포물·설명·노출 범위가 특정되어 있다. |
| 공개 완료 | 사용자가 구체적인 후보의 외부 공개를 승인한 뒤 P7을 수행한다. 비로그인 환경에서 문서와 배포물을 실제로 받아 실행할 수 있고, 최종 로컬 `main`·GitHub `main`·릴리스 태그가 같은 커밋을 가리킨다. 운영 배포도 변경한 경우 실행 이미지의 커밋과 상태까지 대조한다. |

계획과 진행 상태는 이 문서를 기준으로 갱신한다. 실행 결과는 해당 커밋에 대한 비식별 검증 기록으로 연결한다. 최초 계획 커밋 `0f00fe6`은 계획 작성만 담았다. 이후 진행은 아래 현황과 연결한 검증 기록을 따른다.

## 2. 확인한 출발점

2026-09-09에 로컬 작업 트리가 깨끗하고 GitHub `main`이 기준 커밋과 같음을 확인했다. 저장소는 비공개이며 설명과 홈페이지가 비어 있다. 직전 점검에서 태그와 GitHub Release는 0개였다. 공개 직전에 다시 확인한다.

이미 갖춘 기반:

- [MIT 라이선스](../LICENSE), [기여 안내](../CONTRIBUTING.md), [보안 정책](../SECURITY.md), 이슈·PR 템플릿, 한국어·영어 README.
- 실제 PostgreSQL, Vite·Next.js 브라우저 검사, 의존성 감사와 6개 Docker 런타임 검사.
- 서버 모듈 경계, 요청 격리, 연결 중 권한 재검사, 배포 canary와 admission, 자동 배포·실패 복구.
- 핀·필터·리뷰함·알림·재검토, 동시 변경 충돌 처리, 현재 탭의 작성 상태 보존.
- 과거 GitHub DB 18번과 로컬 DB 20번에서 현재 21번까지 데이터 보존을 검사하는 고정 schema fixture.

실행 계획에 영향을 주는 제약:

| 확인 사항 | 계획에 반영할 내용 |
| --- | --- |
| [CI](../.github/workflows/ci.yml)는 조건이 맞는 `main` 푸시에서 운영 배포까지 실행한다. | 준비 작업은 별도 브랜치에서 진행하고, `main` 반영도 배포 단계로 취급한다. |
| Client는 저장소 바깥의 여러 패키지를 상대 경로로 가져오며 npm `bin`이 없다. | `private` 표시만 바꾸는 것으로 배포하지 않는다. 실제 소비자 환경에서 독립 설치를 검증한다. |
| [Compose](../compose.test.yml)는 휘발성 테스트 DB만 제공한다. | 체험용 DB를 테스트 DB와 분리하고 재시작 시 리뷰 데이터가 유지되는 별도 수명 주기를 만든다. |
| [ADR-0005](adr/0005-hosted-and-local-network-modes.md)는 무인증 LAN 공유 모드를 철회했다. | 로컬 체험도 기존 인증형 Gateway를 사용한다. 기존 loopback 개발 예외를 제한적으로 사용하며 별도 LAN 공유 제품을 추가하지 않는다. |
| `ALLOW_INSECURE_HTTP_AUTH`는 loopback 바인딩에서만 허용된다. | Gateway를 호스트에서 실행하는 구성을 먼저 검증한다. 컨테이너 접근을 위해 외부 HTTP 바인딩을 허용하도록 보안 조건을 완화하지 않는다. |
| 기존 canary 스크립트는 명시적 설정으로 로컬 HTTP 검사를 지원한다. | 실제 로컬 canary 성공 후 결과 기록과 admission 승인을 순서대로 실행한다. 운영 HTTPS 검증과 구분해 기록한다. |
| 초기 설정은 `.env`를 자동으로 읽지 않는다. | 체험 실행기가 자신의 설정만 명시적으로 전달하고, 문서와 실제 실행 명령을 일치시킨다. |
| 과거 문서에 개인 컴퓨터의 절대경로와 당시의 미배포 상태가 남아 있다. | 과거 사실은 날짜·커밋과 함께 보존하고 현재 사용자 안내와 구분한다. 링크는 저장소 상대 경로로 고친다. |

기존 검증 결과는 [통합 기록](integration-2026-09-08.md)에 있다. 그 결과를 앞으로 변경될 공개 후보의 검증 결과로 재사용하지 않는다.

## 3. 이번 알파의 범위

### 포함

1. 현재 사용자 문서·변경 이력·공개 설명 정리와 공개 대상 점검.
2. 로컬에서 로그인부터 핀·댓글·알림·재검토까지 체험하는 실행 환경과 Vite 예제 앱.
3. 저장소를 복제하지 않아도 설치할 수 있는 Client 배포물. Vite·Next 연동 패키지도 같은 릴리스에 포함한다.
4. 버전이 고정된 배포물, 설치·업그레이드·백업 복원·롤백 안내와 릴리스 절차.
5. 실제 예제 화면으로 만든 README 이미지와 짧은 시연, 영어·한국어 핵심 사용 안내.
6. 실제로 사용할 수 있는 보안 제보 경로, 지원 범위, 기여자가 작업을 찾을 수 있는 작은 후속 목록.
7. 깨끗한 소비자 환경 검증, 외부 공개 승인 후 공개 및 버전 일치 확인.

### 후속으로 분리

- 프로젝트별 멤버·초대·접근 제어, 서로 신뢰하지 않는 고객이나 팀의 공동 사용.
- 멀티 Gateway 라우팅·고가용성, 관리형 서비스·결제·공개 가입 서비스.
- 외부 이메일·Slack·푸시 알림, 리뷰의 자동 revision 이관, 전체 편집 이력.
- 탭 종료·새로고침 후에도 남는 영속 초안, 로그인 화면 전면 개편.
- npm 레지스트리 게시 및 새 도메인·유료 인프라 도입. 첫 배포는 GitHub Release의 설치 가능한 아카이브로 성립시킨다.

현재 개발자·검토자 권한은 배포 전체에 적용된다는 사실을 README·설치 안내·보안 정책에서 동일하게 설명한다. 고객별 정보 분리가 필요해지면 프로젝트 권한을 선행 작업으로 다시 편성한다.

### P1. 공개 대상과 배포 경계 점검 — 완료

[공개 전 점검 결과](validation/open-source-preflight-2026-09-09.md)에 검사 범위와 발견 사항을 기록했다. 실제 배포 연결 정보를 담은 과거 로그 3개와 개인 경로가 남은 과거 문서 이력은 최종 공개 검토에 포함한다. 향후 배포 설정 마스킹은 P5에서 구현한다.

작업:

- 현재 추적 파일, 공개될 원격 브랜치·태그·커밋 이력, 과거 Actions 로그·아티팩트, 컨테이너와 npm 아카이브에 포함될 파일을 목록화한다.
- 자격 증명·계정 내보내기·DB 백업·운영 설정·개인 경로를 점검한다. 탐지 결과를 확인할 때 비밀 값 자체를 콘솔이나 공개 보고서에 복사하지 않는다.
- 실제 자격 증명이 발견되면 영향과 폐기·교체 대상을 정리한다. 기존 이력·백업을 임의 삭제하거나 강제 푸시하지 않는다. 이력 보존과 공개 범위가 충돌하면 문제 위치와 가능한 공개 방식을 준비해 사용자에게 제시한다.
- 현재 CI의 PR 검증과 운영 게시·배포 경계를 확인한다. 포크의 PR 검사에 운영 비밀이나 쓰기 권한이 필요하지 않고, 포크 자체에 운영 대상이 자동 설정되지 않는지 확인한다.
- 문서·라이선스·배포물에 필요한 제3자 고지의 목록을 만들고, 구현 코드의 권한 모델과 공개 설명을 대조한다.

산출물: 공개 범위 목록, 처리할 항목 목록, 공개 가능한 점검 요약. 민감한 원본 결과는 비추적 비공개 위치에 둔다.

완료 기준: 공개 대상이 특정되고, 실제 발견 사항마다 처리 방법과 검증 방법이 있다. 해결하지 못한 비밀 정보 노출 항목이 있으면 공개를 진행하지 않는다. 현재 파일에서 삭제했다는 이유만으로 과거 이력 문제를 해결한 것으로 판단하지 않는다.

### P3. 로컬 체험 환경과 예제 앱 — 완료

[한 명령 데모 검증](validation/local-demo-2026-09-09.md)에서 `npm run demo`, Vite 예제, 두 사용자 핀·답글·알림·재검토, 재시작 후 DB 보존, 계정 생성 중 강제 종료 복구를 macOS와 Linux에서 확인했다. `d67d097`의 [Linux CI](https://github.com/ddussi/lotur/actions/runs/34251637549)는 스크립트 64개·앱/DB 359개·기존 브라우저 19개·데모 2개, 의존성 감사와 6개 런타임 이미지 검사를 통과했다. npm 설치·이미지 초기화 시간과 캐시 조건을 따로 기록했다. 앞선 [기반 실행 실험](validation/local-demo-probe-2026-09-09.md)은 당시의 기술 검토 기록이다.

초기 확인에서 macOS Node의 `.localhost` 하위 이름 조회 실패와 `CONTROL_HOST`의 포트 거부를 재현했다. 이름 해석은 데모 자식 프로세스에만 적용하는 preload로 보완한다. Control 주소는 명시적 포트를 허용하되 콘텐츠 wildcard 격리는 hostname으로 검증하고, 로그인·영구 링크에 해당 포트를 보존한다. 기존 기본 포트 설정과 인증·외부 HTTP 제한은 유지한다.

기본 설계:

- 별도 `compose.demo.yml`로 로컬 전용 PostgreSQL과 영속 볼륨을 관리하고, Node.js 실행기가 호스트의 loopback에서 Gateway·Client·예제 앱을 관리한다.
- `examples/vite-review/`에 실제로 핀을 꽂고 수정할 수 있는 작은 예제 앱을 둔다. 기존 테스트 fixture의 개념을 재사용하되 예제가 테스트 전용 파일을 가져오지 않도록 한다.
- Node.js 24와 Docker Compose 설치를 전제로, 의존성 설치 후 하나의 체험 실행 명령으로 시작할 수 있게 한다. 구체적인 명령 이름은 구현 시 확정해 문서와 일치시킨다.
- 기존 인증 서비스·DB migration·canary·admission 경로를 사용한다. 체험 전용 개발자·검토자 계정과 무작위 비밀 값을 생성하고, 프로세스 인자·공개 로그에 비밀 값을 남기지 않는다.
- `control.localhost`와 콘텐츠 하위 호스트의 해석을 실제 지원 환경에서 검사한다. 시스템 DNS나 hosts 파일 수정이 필요한 경우 자동 변경하지 않고 이유와 대안을 문서화한다.
- 종료는 실행기가 소유한 프로세스·컨테이너만 정리하고 데이터는 보존한다. 체험 데이터 삭제는 별도 명령으로 구분하고 삭제 대상을 표시한다.
- 운영 DB URL·운영 도메인·기존 서버 설정을 체험 설정으로 가져오지 않는다. 개발용 HTTP 예외는 loopback에만 적용한다.

처음에 검증할 기술 항목: 호스트 이름 해석, 제어/콘텐츠 호스트 분리, DB 권한 초기화, 로그인과 비밀번호 변경, 실제 canary → 결과 기록 → admission 승인, 새 공유 URL에서 리뷰 초기화. 이를 작은 실행으로 확인한 뒤 편의 실행기를 완성한다.

완료 기준:

- 깨끗한 환경에서 문서대로 시작하고, 두 브라우저 사용자로 로그인 → 핀·댓글 → 답글·알림 → 처리 → 재검토를 끝낸다.
- 공유 중지 후 리뷰함에서 내용을 확인하고, 체험 환경 재시작 후 기존 리뷰·답글·알림이 유지된다.
- 포트 충돌, Docker 미실행, 초기화 실패, 재실행, 중간 종료 시 이유를 안내하고 남은 자원을 정리한다. 다른 프로세스나 기존 데이터를 종료·초기화하지 않는다.
- 개발용 HTTP 설정을 외부 인터페이스로 바꾸면 기존 구성 검사가 거부한다. 인증 없이 리뷰 데이터를 읽을 수 없다.
- macOS의 실제 환경과 Linux CI에서 실행한다. 최초 다운로드·빌드 시간과 준비 후 체험 시간을 따로 기록한다. 준비 후 첫 댓글까지 10분 이내를 사용성 목표로 측정하며, 검증 전 성능 약속으로 게시하지 않는다.

### P4. 독립 Client 배포와 소비자 설치 — 완료

`npm run pack:client`와 [양 언어 설치 안내](client-installation.md)를 구현했다. [Client 소비자 검증](validation/client-package-2026-09-09.md)에서 빈 캐시의 오프라인 설치, 실제 터미널 숨김 비밀번호, 실제 Gateway 공유·리뷰 저장·재연결·종료·리뷰 연결 실패 정리를 macOS와 Linux에서 확인했다. 포장된 Vite/Next 연동 파일을 앱에 설치한 브라우저 시나리오와 6개 이미지도 [Linux CI](https://github.com/ddussi/lotur/actions/runs/34253902398)를 통과했다.

기본 설계:

- 기존 Client 소스를 한 곳에서 유지하며, 필요한 내부 모듈만 포함한 생성용 배포 디렉터리와 명시적인 `bin` 진입점을 만든다.
- GitHub Release에 설치 가능한 Client `.tgz`, Vite·Next 연동 `.tgz`, 파일 해시와 필요한 라이선스를 제공한다. 첫 릴리스는 npm 계정·패키지 이름 확보에 의존하지 않는다.
- 외부 런타임 의존성은 manifest와 잠금 파일 또는 포함 정책으로 명시한다. 배포물에 개발용 서버·DB 코드와 불필요한 개발 의존성을 넣지 않는다.
- monorepo 상대 import와 symlink에 기대지 않고 동작하도록 빌드·포장한다. 생성물을 별도로 수작업 수정하지 않는다.
- `--help`와 `--version`, 비밀번호 프롬프트, 오류 종료 코드, `Ctrl+C`, 재연결, 리뷰 binding 실패 정리를 배포된 명령에서 확인한다.

대상: `apps/client`, 필요한 패키지 메타데이터·빌드/포장 스크립트, `scripts/integration-packages.test.mjs`, 사용 안내.

완료 기준:

- 저장소 밖의 빈 디렉터리와 격리된 설치 위치에서 아카이브만 받아 설치·실행한다. `NODE_PATH`, monorepo `node_modules`, 전역에 이미 설치된 패키지에 의존하지 않는다.
- 포장된 Client로 로컬 체험 Gateway에 로그인하고 공유·리뷰 binding·종료를 완료한다.
- 포장된 Vite·Next 패키지로 예제 연동을 확인하고 production 빌드에 리뷰 script가 기본 활성화되지 않는 기존 검사를 유지한다.
- 아카이브에 비밀 설정·테스트 데이터·실행 로그·불필요한 파일이 없고, 버전과 라이선스가 정확하다.

### P5. 릴리스·업그레이드·기여 자료 완성

`0.1.0-alpha.1` 버전과 후보 파일 생성·검증을 구현했다. [초기 후보 검증](validation/release-files-2026-09-09.md)에서 macOS 두 번의 빌드와 성공한 Linux CI의 8개 파일이 모두 일치했다. 기존 배포 접속 정보는 같은 production 환경의 Secret에 복사했고 준비 브랜치의 참조를 변경했다. 6개 후보 이미지의 별도 수동 게시·digest 검증 절차는 구현했으며, 실제 레지스트리 검증을 진행한다. 실제 예제의 [화면 3개와 짧은 영상](media/README.md), 양 언어 README 연결, 최신 알파 지원 방침과 [기여 로드맵](roadmap.md)을 추가했다. DB 복원·업그레이드 검증과 공개 시 보안 제보 경로 활성화는 남아 있다.

작업:

- 예정 버전 `v0.1.0-alpha.1`과 root/workspace/lockfile/배포물 버전을 일치시킨다. 후보를 선택한 뒤 그 커밋을 기준으로 파일 목록·해시·이미지 digest를 기록한다.
- 기존 `main` 자동 배포를 보존하면서 별도 릴리스 후보 빌드 절차를 추가한다. 입력 커밋의 검증 결과를 확인하고, 릴리스 게시나 태그 푸시만으로 운영 배포가 시작되지 않도록 한다.
- 지원할 6개 Docker 런타임의 버전별 배포를 준비한다. 지원 CPU 아키텍처는 실제 빌드·실행한 것만 기재하고, 검증하지 않은 multi-arch 지원을 표시하지 않는다.
- 기반 이미지도 공개 후보에서 다시 점검한다. 복원 도구 문서 점검 중 [PostgreSQL 17.11 보안 업데이트](https://www.postgresql.org/about/news/postgresql-186-1711-1615-1519-1424-and-19-beta-3-released-3365/)를 확인했다. 기존 17.6 기반은 공개 전 공식 17.11 digest로 갱신하고, 새 DB·백업/복원 도구로 검증한다. 과거 17.6 검증 기록과 현재 운영 DB는 이 준비 변경만으로 수정하지 않는다.
- migration 18의 운영 이력을 유지하고 19–21을 추가한 이유, 이전 로컬 DB의 다른 번호 사용, 반복 migration 안전성을 업그레이드 안내에 적는다.
- 데이터가 있는 후보 DB의 백업을 빈 DB로 복원하고, 리뷰·답글·알림·권한과 적용 기록을 비교한다. 이전 앱 이미지로 복귀 가능한 DB 호환 범위를 실제로 확인하고, 앱 롤백과 DB 복원을 별개 절차로 설명한다.
- 실제 예제 데이터로 핀 화면·리뷰함·재검토 이미지와 짧은 시연을 만든다. 이미지에 대체 텍스트를 넣고 개인 계정·실제 운영 주소를 포함하지 않는다.
- `SECURITY.md`에 최초 지원 버전과 업데이트 경로, 공개 후 실제 활성화할 비공개 제보 경로를 적는다. 활성화 전에는 활성화되었다고 표시하지 않는다.
- 기여 안내에 작은 문서·예제·테스트 작업과 후속 로드맵을 정리한다. 지원 플랫폼, 알려진 한계, 버그 재현 방법을 일관되게 유지한다.

완료 기준: 릴리스 초안에 설치 파일·지원 범위·업데이트 방법·검증 근거가 모두 있고, 다운로드할 파일이 어떤 커밋에서 만들어졌는지 추적할 수 있다. 실제 복원 검사 결과가 있으며, 롤백 시 데이터 영향이 설명되어 있다.

### P6. 공개 후보 통합 검증

변경 중에는 해당 기능의 검사를 실행한다. 최종 후보에서는 아래 전체 검사를 한 번 완주한다. 이후 변경·실패·미해결 우려가 생긴 경우에만 영향을 받는 검사를 다시 실행한다.

| 영역 | 검사 | 통과 조건 |
| --- | --- | --- |
| 정적·빌드 | `npm run check:style`, `typecheck`, `check:boundaries`, `build` | 경계·타입·생성 UI 일치 검사 통과 |
| 기존 전체 기능 | 격리 PostgreSQL의 `TEST_DATABASE_URL`과 함께 `npm run check:mvp` | 스크립트·앱·DB·브라우저 검사 통과, 예상하지 않은 skip 없음 |
| DB 업그레이드 | 기존 GitHub 18·로컬 20 fixture → 후보 migration, 반복 실행 | 리뷰·핀 번호·답글·상태·알림·적용 시각 보존 |
| 인증·권한 | 미로그인 거부, 역할 분리, 권한 회수, 알림 수신자 분리 | 기존 보안 동작 유지 |
| 동시성·작성 상태 | 동시 재검토·수정, 이벤트 재동기화, 제출 중 입력·실패·IME 조합 | 충돌을 알리고 다른 변경과 작성 내용을 조용히 덮어쓰지 않음 |
| 첫 체험 | 새 환경의 시작·리뷰·종료·재시작, 오류 처리 | 문서대로 실행되고 저장 데이터·자원 수명 주기 일치 |
| 소비자 배포물 | 저장소 밖에서 Client·연동 패키지 설치 및 실제 공유 | 내부 소스나 미게시 workspace 패키지를 요구하지 않음 |
| 런타임 이미지 | 6개 Docker target 빌드·entrypoint·잘못된 설정 거부 | 기존 CI 수준 유지, 게시 대상과 검사 대상 일치 |
| 의존성·포장 | `npm audit --omit=dev`, 배포 manifest·라이선스·포함 파일 검사 | 발견된 배포 관련 문제를 처리하고 검증 범위를 기록 |
| 백업·복원 | 후보 DB dump → 빈 DB 복원 후 기능 검사 | 데이터와 권한 유지, 실패 시 복구 절차 재현 가능 |
| 문서·제품 자료 | 상대 링크, 실제 명령, 양 언어 기능표, 이미지 검수 | 깨진 안내·개인 정보·미구현 약속 없음 |
| 운영 경로 | 별도 후보 환경의 DNS/TLS/proxy, canary, 전용 계정 브라우저 검사 | 운영 승격에 필요한 HTTPS 동작 검증; 로컬 HTTP 검사로 대체하지 않음 |

Windows 네이티브와 Firefox·Safari 등 검사하지 않은 환경은 검증 완료로 표시하지 않는다. 기존의 Linux·macOS/Chrome 검증 범위와 추가 실행 결과를 구분한다.

실행 증거에는 후보 커밋, Node·DB·브라우저·Docker 버전, 명령과 통과/실패/skip, 설치 아카이브 해시, 이미지 digest, 알려진 한계를 기록한다. 운영 비밀 값과 원본 사용자 데이터는 포함하지 않는다.

### P7. 최종 공개·배포·버전 일치

공개 승인 전에 준비할 구체적인 검토 자료:

1. 공개할 저장소와 이력·Actions 로그·아티팩트의 노출 범위 및 점검 결과.
2. 검증한 커밋, 변경 diff, 공개 설명·README 화면·릴리스 노트.
3. 설치 파일·체크섬·이미지 목록, 실제 설치·DB 복원·운영 경로 검증 결과.
4. 필요한 저장소 설정 변경, 운영 배포 영향과 복구 방법, 알려진 제한.

저장소 공개 전환과 최초 외부 릴리스 게시에 대한 승인은 위 자료를 모두 준비한 뒤 한 번에 요청한다. GitHub의 공개 전환은 코드뿐 아니라 과거 Actions 로그도 외부에 보이게 하므로 준비 단계의 구현·검사와 구분한다. 현재 요청으로 승인된 계획·구현·비공개 검증은 계속 진행한다.

승인 후 실행:

- 공개 후보 이후 원격 변경이 없는지 확인하고, 있다면 보존하며 통합 후 영향을 받는 검사를 다시 수행한다.
- 검증한 최종 커밋을 `main`에 반영한다. 기존 자동 배포가 실행되면 완료까지 확인하고, 환경별 배포 ID/config digest·canary·admission과 실행 이미지 revision을 대조한다.
- 정확한 최종 커밋에 릴리스 태그를 만들고 검증한 배포물을 게시한다. 기존 태그를 다른 내용으로 덮어쓰지 않는다.
- 승인한 저장소 공개 전환과 배포물 공개 설정을 적용하고, 실제 보안 제보 경로를 활성화·확인한다.
- GitHub 로그인 정보와 로컬 npm 캐시가 없는 소비자 환경에서 문서·릴리스·이미지 접근, 설치, `--version`, 첫 사용을 다시 확인한다.
- 로컬 `main`·GitHub `main`·태그의 커밋, 릴리스 파일 해시, 해당하는 운영 이미지 revision을 함께 기록한다. 작업 트리를 정리하고 기존 백업은 유지한다.

위 결과가 확인되어야 지속 목표를 완료 처리한다. 승인 대기, 후보 검증 실패, 일부 산출물 미게시 상태는 완료로 기록하지 않는다.

커밋은 완료된 작업 단위로 나눈다. 한 단계가 너무 크면 구현과 관련 검증을 함께 담는 작은 커밋으로 나눈다.

| 묶음 | 범위 |
| --- | --- |
| 계획·공개 점검 | 이 문서, 공개 가능한 점검 결과, 필요한 노출 항목 정리 |
| 문서 정리 | 현재/과거 안내 구분, 양 언어 안내, 변경 이력 |
| 로컬 체험 | Compose·실행기·예제·시작/종료/재시작 검증 |
| Client 배포 | 빌드·포장·명령 진입점·외부 설치 검증 |
| 릴리스 준비 | 후보 생성 절차·버전 관리·업그레이드/복원 안내 |
| 제품·지원 자료 | 시연·README 이미지·보안 및 기여 안내 |
| 최종 검증 수정 | 실제 후보 검증에서 발견한 문제와 재검증 결과 |

기존 Gateway의 구조나 인증 모델 변경이 필요해지면 먼저 이유와 영향 범위를 이 계획에 기록한다. 편의 기능 때문에 기존 보안 검사를 삭제하거나 통과 기준을 낮추지 않는다. DB 변경이 추가로 필요한 경우 적용된 1–21번을 수정하지 않고 새 번호와 과거 DB 업그레이드 검사를 추가한다.

예상하지 않은 사용자 변경은 보존하고 기준 커밋과 통합 범위를 다시 확인한다. 작업 진행을 위해 과거 커밋이나 운영 리뷰 데이터를 삭제하지 않는다.
