**Review Tunnel 개선 실행안 — 소규모 내부 팀**

작성일: 2026-09-07. 상태: 제안 및 구현 계획. 제품 코드는 이 보고서 작성 과정에서 변경하지 않았다.

사용자가 선택한 대상은 소규모 내부 팀이다. 계획은 개발자와 검토자 합계 3–8명, 동시에 검토하는 프로젝트 1–3개를 가정한다. 인원과 프로젝트 수는 일정·검증 규모를 정하기 위한 가정이며 실제 사용량 측정값은 아니다. 한 배포를 서로의 프로젝트를 열람할 수 있는 하나의 내부 팀으로 취급한다.

가장 먼저 출시할 묶음은 **댓글의 저장·갱신 신뢰성, 패널 접기, 미해결 필터, 화면 안에서의 편집**이다. 다음 묶음은 **터널 종료 후에도 사용하는 리뷰함, 영구 댓글 링크, 페이지를 넘나드는 알림과 재검토 요청**이다. 각 묶음은 독립적으로 사용할 수 있게 출시한다.

앞선 커밋 리뷰에서는 기존 애플리케이션·DB 테스트 총 328개, 기존 리뷰 오버레이 브라우저 테스트 1개, 타입 검사를 통과했다. 별도 재현으로 초안 손실, 오래된 댓글의 갱신 누락, DB 이벤트 순서 문제, 한국어 본문의 바이트 제한 충돌을 확인했다. 이는 커밋 사본의 검증 결과이며 이번 문서 작업에서 현재 작업 트리의 전체 테스트를 다시 실행했다는 뜻은 아니다. 제품 사용 효과와 소요 시간은 아직 사용자 파일럿으로 검증하지 않았다.

**목표 사용자 흐름은 한 번의 피드백이 확인 완료까지 이어지는 것이다.** 검토자는 공유 화면에서 앱을 조작하다가 필요한 순간 패널을 열고 댓글을 남긴다. 개발자는 리뷰함에서 `/products`와 `/cart`의 미해결 항목을 함께 확인한다. 댓글을 열면 기존 대화와 핀이 연결되고, 수정 후 작성자에게 재검토를 요청한다. 작성자는 알림에서 해당 댓글로 이동해 확인 완료하거나 보완을 요청한다. 개발자의 터널이 종료되어도 리뷰함의 대화와 처리 기록은 남는다. 실제 앱을 다시 볼 수 있는 시점과 기록을 읽을 수 있는 시점을 UI에서 구분한다.

1차 성공 기준은 기능 개수가 아니라 다음 다섯 작업의 완수다.

1. 다른 사용자가 댓글을 남기는 동안 작성하던 답글을 잃지 않는다.
2. 전체 목록을 순회하지 않고 현재 페이지의 미해결 피드백을 찾는다.
3. 지금 보고 있지 않은 페이지의 답글이나 재검토 요청을 발견한다.
4. 새 터널 URL을 전달받지 않아도 기존 댓글 링크로 같은 대화에 도착한다.
5. 개발자가 수정한 항목을 원래 작성자가 확인하고 완료한다.

**단계 0은 새 기능의 기반이 되는 저장·갱신 동작을 바로잡는다.** 네 문제를 하나의 큰 리팩터링으로 묶지 않고 화면 상태와 저장소 동시성으로 나누어 수정한다.

이벤트 잠금은 `recordReviewEvent` 끝부분에만 추가하지 않는다. 공통 트랜잭션 진입에서 획득하고 계정·binding·thread 잠금보다 먼저 적용해 모든 쓰기의 잠금 순서를 통일한다. 읽기는 이 쓰기 잠금에 참여하지 않는다. 기존 전역 이벤트 보존 정리도 같은 쓰기 순서 안에서 수행한다. 동시 쓰기를 직렬화하는 비용이 있으므로 단계 4에서 대기 시간과 처리량을 측정하고, 작은 팀의 목표를 충족하지 못하면 이벤트 발행 구조를 별도 개선한다.

원격 답글 변경을 정확히 갱신할 수 있도록 이벤트에 필요할 때 `contentType`·`contentId`를 추가하고, 인증된 단건 댓글·답글 조회를 제공한다. 본문은 이벤트에 넣지 않는다. 콘텐츠 version과 클라이언트의 요청 세대 번호를 비교하고, 같은 스레드의 재조회를 직렬화해 오래된 응답이 새 상태를 덮지 않게 한다. 상태 변경 도중 시작된 읽기 응답도 폐기하고 변경 후 다시 조회한다. 영속 상태 version은 단계 3에서 추가한다. 이벤트가 보존 기간을 벗어난 경우에는 재연결된 클라이언트가 현재 보고 있는 범위를 다시 읽는다. 새 이벤트가 우연히 발생할 때까지 기다리는 복구는 허용하지 않는다.

저장 실패 시에는 입력을 유지한다. 서버가 명확하게 거절한 경우만 실패 사유와 재시도를 제공하고, 연결 단절로 저장 여부를 모르는 경우에는 상태 확인을 안내한다. 무조건 자동 재전송하는 동작은 넣지 않는다. 재시도 자동화를 추가할 때는 먼저 생성 요청의 중복 방지 키와 서버의 처리 결과 조회를 설계한다.

초안은 1차에 같은 문서가 살아 있는 동안의 메모리 상태로 보존한다. 경로를 갔다 돌아오는 경우와 SSE 갱신은 보존 대상이고, 새로고침·탭 닫기 뒤 복구는 후속 범위다. 댓글 내용은 localStorage에 자동 저장하지 않는다. 패널 열림·필터 같은 비민감 표시 설정만 sessionStorage에 저장한다. 권한 상실이나 계정 변경이 확인되면 해당 계정의 메모리 초안을 지운다.

필터는 `status`와 `author=me`를 명시적으로 검증하고, 댓글 페이지 커서에는 필터·정렬 문맥을 묶는다. 다른 필터에서 발급된 커서는 거부하거나 첫 페이지로 초기화한다. 1차 목록 정렬은 기존의 생성 시각·ID 순서를 유지한다. 최근 답글 기준으로 목록이 계속 움직이는 정렬은 알림을 통해 보완하고, 별도 요구가 확인되면 추가한다. 응답은 필터 결과 수와 전체 미해결 수를 구분한다.

패널에 검색창을 먼저 추가하지 않는다. 내부 파일럿에서 상태·작성자·페이지 필터만으로 충분한지 확인한 뒤 본문 검색을 검토한다. 검색을 추가할 경우에도 서버에서 전체 결과를 조회하며, 이미 불러온 100개에만 검색을 적용하지 않는다.

**단계 2는 영속 데이터에 영속 접근 경로를 제공한다.** 리뷰함은 Control host의 로그인된 화면으로 제공하고, 앱 안의 오버레이는 계속 Content host에서 동작한다. 두 화면이 같은 리뷰 도메인 서비스를 사용하도록 한다.

| 화면 | 표시 내용 | 기본 행동 |
| --- | --- | --- |
| 프로젝트 목록 | 소유자·프로젝트 이름·미해결 수·최근 활동 시각 | 내가 소유한 프로젝트를 먼저 표시하되, 같은 내부 팀이 열람 가능한 전체 프로젝트로 전환 가능 |
| 프로젝트 리뷰함 | 선택한 버전, 페이지별 미해결 수, 상태·작성자 필터, 스레드 요약 | 프로젝트 내 여러 페이지를 한 번에 확인. 과거 버전을 명시적으로 선택 가능 |
| 스레드 상세 | 원래 path·버전·핀 번호·본문·답글·처리 상태 | 터널 없이도 답글 작성과 허용된 상태 변경. 실제 앱이 열릴 때만 `앱에서 보기` 제공 |
| 내 알림 | 페이지·프로젝트를 넘는 수신자 본인의 알림 | 알림에서 영구 스레드 링크로 이동. 읽음 상태는 성공적인 열람 후 변경 |

초기 기본 버전은 마지막으로 사용자가 선택한 버전, 없으면 가장 최근 생성된 버전이다. 과거 버전의 미해결 수를 별도로 표시해 기본 버전 선택으로 남은 피드백을 숨기지 않는다. revision key는 현재 앱이 해당 Git 커밋의 불변 스냅샷이라는 증거로 표시하지 않는다. HMR이나 미커밋 수정으로 앱 내용은 바뀔 수 있으므로 `검토 기준`이라는 의미와 현재 공유 상태를 구분한다.

내부 팀 1차의 접근 정책은 현재 배포 전체의 DEVELOPER·REVIEWER 범위를 유지한다. 이 팀의 프로젝트 이름과 리뷰 기록은 해당 역할을 가진 다른 팀원에게도 보인다. ADMIN만 있는 계정에는 리뷰 권한을 자동 부여하지 않는다. 기존 작성자 편집·개발자 처리 권한도 공통 정책 함수로 유지한다. 프로젝트 목록을 제공하면 기존의 URL 기반 발견 가능성이 넓어진다는 점을 파일럿 안내에 명시한다. 비공개 프로젝트나 외부 인원이 필요해지면 프로젝트별 접근 목록을 먼저 구현한다.

서비스에는 인증된 `ReviewAccessContext`를 서버가 만드는 경로를 도입한다. Content 경로는 활성 binding에서 project·revision을 확인하고, Control 경로는 현재 계정 권한과 영속 project·revision에서 문맥을 확인한다. 클라이언트가 보낸 projectId나 역할만으로 문맥을 신뢰하지 않는다. 기존 메서드에서 binding 검사를 단순히 삭제하는 방식은 사용하지 않는다. 터널 연결 생성·종료는 그대로 binding을 기준으로 처리한다.

Control API는 기존 CLI 전용 `clientControlExtension`과 별도로 브라우저용 adapter를 둔다. 기존 Control 세션 Cookie·재인증 상태·정확한 Origin·요청 크기·동시 처리 제한을 재사용한다. 앱 오버레이에는 Control Cookie나 bearer를 전달하지 않는다. Control 서버 렌더링 화면에는 초기 목록을, 별도 정적 모듈에는 필터·편집 동작을 맡기는 구성이 1차 권고안이다. 별도 프런트엔드 프레임워크 도입은 요구하지 않는다.

새 경로와 서비스는 다음 수준으로 나눈다. 아래 이름은 구현 제안이며 현재 존재하는 API가 아니다.

| 접근 경로 | 제안 계약 | 용도 |
| --- | --- | --- |
| Content API | `GET /_review-tunnel/review/comments/:threadId` 및 해당 답글 단건 GET | 이벤트 변경 대상 재조회와 선택 스레드 로딩 |
| Control 화면 | `GET /reviews`, `/reviews/projects/:projectId`, `/reviews/threads/:threadId` | 로그인된 영속 리뷰함·영구 링크 |
| Control API | `GET /api/reviews/projects`, `/projects/:id/revisions`, `/projects/:id/threads` | 서버 필터와 페이지 분할을 적용한 목록 |
| Control API | `/api/reviews/threads/:id` 및 `/replies`, `/status` | 터널과 독립된 허용 범위의 읽기·답글·상태 변경 |
| Control API | `GET /api/reviews/notifications` 및 알림 읽음 변경 | 수신자 전체 알림 목록·전체 미확인 수 |
| 실시간 갱신 | Content의 기존 SSE와 Control의 계정별 변경 알림 | 본문 전송 없이 영향을 받은 화면만 재조회 |

스레드 ID는 전역 고유 식별자를 사용하고 소유자 slug를 링크의 권한 경계로 삼지 않는다. 모든 스레드 조회에서 저장된 project·revision 관계와 접근 정책을 다시 확인한다. 삭제된 스레드 링크는 삭제 표시와 남은 답글을 보여 주며, 허용 범위 밖 링크는 콘텐츠를 반환하지 않는다.

영구 댓글 링크는 Control의 `/reviews/threads/:threadId`로 고정한다. 로그인 전 열어도 로그인 후 해당 스레드로 돌아오게 한다. return path는 내부 리뷰 경로만 허용하고 외부 URL은 받지 않는다. 로그인 후 다른 사용자로 전환되면 대상 접근 권한을 다시 평가한다.

`앱에서 보기`는 해당 project·revision에 정확히 일치하는 현재 활성 터널만 연결한다. 일치하는 터널이 여러 개면 사용자가 선택하고, 한 개면 바로 연결하며, 없으면 상세 화면에 공유 종료 상태를 표시한다. 만료되지 않은 DB binding만으로 온라인 상태를 확정하지 않는다. 1차는 요청을 처리하는 Gateway가 확인하는 로컬 활성 세션만 연결 후보로 표시한다. 다른 인스턴스에서만 열린 공유는 상태 확인 불가로 안내하며, 인스턴스 간 활성 공유 목록은 후속 운영 요구로 둔다.

스레드 선택 정보를 앱 자체 query나 hash에 무조건 추가하지 않는다. 기존 로그인 교환 절차에 결합할 수 있는 짧은 수명의 일회성 이동 문맥을 서버에 두고, 정확한 대상 Content host·계정·세션·revision에 묶는다. Content의 예약 경로에서 문맥을 소비한 뒤 저장된 정상 path로 이동하고 오버레이가 선택 스레드를 가져온다. 이 문맥은 로그인 권한을 대신하지 않는다. 앱의 기존 query·hash 라우팅과 충돌하지 않는지 구현 착수 시 작은 검증을 먼저 한다.

Query나 hash에 따라 다른 화면을 보여 주는 앱은 현재 path만으로 화면 상태를 정확히 복원할 수 없다. 1차 링크는 저장된 path·스레드를 복원하는 범위로 한정하고, 파일럿 앱에서 해당 상태가 핵심이면 프로젝트별 허용 query 키 또는 앱이 제공하는 화면 상태 식별자를 먼저 설계한다. token·검색어 등의 원본 query 전체 저장은 기본 동작으로 추가하지 않는다.

리뷰함의 목록 요약은 답글 전체를 포함하지 않는다. 미해결 수·페이지별 집계·알림 미확인 수는 표시 중인 한 페이지 길이가 아니라 서버 전체 결과로 계산한다. 알림은 기본 50개 단위의 안정 커서를 제공한다. 프로젝트·revision·상태·작성자·정렬에 맞춘 인덱스는 실제 조회 계획으로 확인하고, 불필요한 조합 인덱스를 미리 모두 만들지는 않는다.

**단계 3은 답변과 재검토가 필요한 사람에게만 내부 알림을 제공한다.** 현재의 멘션 알림에 새 답글과 재검토를 더하되, 작은 팀에서도 알림이 반복되지 않도록 수신 규칙을 고정한다.

| 계기 | 기본 수신자 | 중복·읽음 처리 |
| --- | --- | --- |
| 멘션 | 현재 허용되는 참여자 중 명시적으로 언급된 사람 | 자기 자신 제외. 같은 변경에서 답글 알림과 겹치면 하나로 표시 |
| 새 답글 | 원댓글 작성자와 이미 답글을 남긴 참여자 | 작성자 본인·비활성 계정 제외. 이미 읽은 알림을 새 답글 없이 다시 만들지 않음 |
| 재검토 요청 | 원댓글 작성자 | 같은 요청의 재시도는 한 번만 생성. 작성자가 비활성이면 개발자에게 이유 안내 |
| 확인 완료·보완 요청 | 재검토를 요청한 개발자 | 요청 회차와 결과를 연결해 다른 회차의 알림을 읽음 처리하지 않음 |

알림에 `kind`와 원인이 된 이벤트 식별자를 추가하고 `(recipient, source event)` 중복 방지 규칙을 둔다. 원인 식별자는 알림의 중복 방지 값으로 보관하며 SSE 이벤트 보존 정리가 알림을 연쇄 삭제하게 연결하지 않는다. 기존 멘션은 MENTION으로 이행한다. 알림 수신자나 참여자 정보가 다른 사용자 응답에 섞이지 않게 한다. 알림 버튼 클릭만으로 먼저 읽음 처리하지 않고, 스레드를 성공적으로 불러온 뒤 읽음 처리한다. 기본으로 페이지 전체의 댓글 변경을 모든 사용자에게 알림으로 보내지는 않는다.

멘션 입력에는 허용된 참여자 범위의 자동완성을 제공한다. 첫 참여 이전의 사람을 찾지 못하는 이유와 참여자 범위를 UI에서 설명한다. 내부 계정 전체를 임의 검색해 멘션 대상 범위를 넓히는 변경은 포함하지 않는다. 계정별 알림 스트림은 열린 탭당 하나를 사용하며 기존 연결 상한을 반영한다. 알림 기능 때문에 콘텐츠 페이지마다 프로젝트별 스트림을 여러 개 더 열지 않는다. 상태가 불확실하면 목록 재조회로 복구하고, 로그인 만료·권한 회수 시 종료한다.

재검토는 다음 상태를 제안한다. 기존 OPEN·RESOLVED 데이터는 그대로 유지하고 NEEDS_REVIEW를 추가한다.

| 현재 상태 | 행동 | 다음 상태 | 허용 주체 |
| --- | --- | --- | --- |
| OPEN | 재검토 요청 | NEEDS_REVIEW | 현재 DEVELOPER 권한을 가진 사용자 |
| NEEDS_REVIEW | 확인 완료 | RESOLVED | 원댓글 작성자 또는 DEVELOPER |
| NEEDS_REVIEW | 보완 요청 | OPEN | 원댓글 작성자 또는 DEVELOPER |
| NEEDS_REVIEW | 요청 취소 | OPEN | DEVELOPER |
| OPEN | 바로 해결 | RESOLVED | DEVELOPER, 처리 기록에 직접 해결임을 표시 |
| RESOLVED | 다시 열기 | OPEN | DEVELOPER |

NEEDS_REVIEW에서도 답글은 허용한다. 원댓글이 삭제된 스레드는 새 재검토 요청을 받지 않는다. 개발자의 직접 해결을 남겨 사소한 항목마다 확인 단계를 강제하지 않는다. 원댓글 작성자도 현재 유효한 리뷰 접근 권한이 있어야 확인·보완을 요청할 수 있다.

상태 변경은 `workflow_version`을 함께 비교해 OPEN→NEEDS_REVIEW→OPEN처럼 상태 문자열이 같아진 뒤 오래된 요청이 성공하는 일을 막는다. 본문 편집 version과 상태 version은 분리한다. 요청자·대상 작성자·요청 시각·요청 회차·결과를 영속 처리 기록으로 남긴다. 보존 기간이 짧은 SSE 이벤트를 장기 재검토 기록으로 사용하지 않는다. 전체 본문 편집 이력을 새로 보관하는 것은 이번 범위가 아니다.

**버전 간 이어 보기는 내부 파일럿 이후 별도 묶음으로 검토한다.** 단계 2에서 과거 버전의 리뷰를 조회하는 것은 포함하지만, 자동 승계는 포함하지 않는다. 같은 검토 기준으로 수정·재검토하는 흐름을 먼저 검증하고 실제로 버전 전환에서 피드백이 누락될 때 추가한다.

추가 시에는 동일 프로젝트 안의 이전 미해결 댓글을 선택해 새 버전에 연결한다. 기존 댓글을 이동하거나 과거 상태를 덮어쓰지 않는다. 새 스레드에 원본 링크·원래 버전·가져온 사람을 남기고 `(source thread, target revision)`으로 중복 가져오기를 막는다. 답글 전체를 자동 복사하지 않고 원본 대화를 열 수 있게 한다. 요소 anchor도 새 화면에서 식별 가능함을 확인하기 전까지는 핀을 보류하며, 사용자가 새 위치를 지정할 수 있게 한다. 이 작업은 별도 3–5일의 추가 추정이며 14–25일에 포함하지 않는다.

프로젝트별 접근 목록은 외부 사람을 초대하거나 팀 내부에 비공개 프로젝트가 생기는 시점의 선행 작업이다. 먼저 기존 내부 계정을 소유자·관리 참여자·검토 참여자로 지정하는 기능을 만들고, 이후 만료·회수 가능한 외부 초대 흐름을 더한다. 기존 프로젝트의 참여자 이행, 마지막 소유자 제거 금지, 기존 Control·Content·SSE의 권한 회수까지 포함하므로 별도 계획이 필요하다. 내부 팀 1차 일정에는 넣지 않는다.

스크린샷 첨부, Slack·이메일 알림, 담당자·마감일·태그, 본문 전체 검색, GitHub 연동, 브라우저 간 초안 동기화는 파일럿에서 실제 방해 요인이 확인될 때 확장한다. 현재 팀의 기본 검토 흐름을 완성하는 동안에는 앞선 단계의 완료 기준에 집중한다.

**코드 작업은 작은 검토 단위로 나눈다.** 다음 작업 묶음은 향후 PR 경계를 제안한 것이며, 현재 PR을 생성하거나 코드를 구현한 상태가 아니다. 같은 행의 작업일을 앞의 단계 일정에 다시 더하지 않는다.

| 작업 묶음 | 변경 지점 | 검토자가 확인할 핵심 | 의존 |
| --- | --- | --- | --- |

오버레이는 현재 하나의 긴 문자열에 UI·상태·네트워크가 모여 있다. 단계 A와 C에서 바뀌는 부분을 중심으로 편집 상태·목록 상태·알림·anchor 렌더링의 책임을 분리한다. generic bootstrap URL, CSP nonce 전달, Vite·Next adapter와 정적 자산의 배포 경로는 유지한다. 별도 대규모 UI 재작성이나 공유 relay protocol 변경은 이 기능 계획에 필요하지 않다. 실제 파일 분리 방식은 기존 build·Docker·패키지 경계 검사를 통과하는 범위로 정한다.

리뷰함 서비스에서는 도메인 객체에 HTTP Cookie·URL 객체를 전달하지 않는다. Gateway가 인증과 전달 경로를 해석하고, `packages/review`는 검증된 접근 문맥과 명령을 받으며, PostgreSQL 저장소가 현재 계정·상태·version을 트랜잭션 안에서 확인한다. 메모리 저장소와 PostgreSQL 저장소의 결과 계약을 함께 변경해 브라우저 fixture만 통과하는 구현이 되지 않게 한다.

**DB 변경과 배포는 기능을 켜는 시점을 분리한다.** 단계 A–D는 가능한 한 기존 schema와 API를 유지하면서 새 조회·선택 입력을 추가한다. E–H에는 알림 종류·중복 방지와 필요한 인덱스를, I에는 상태 확장·workflow version·영속 처리 기록을 추가한다. 마이그레이션은 빈 DB와 현행 DB 양쪽에서 반복 실행 가능해야 한다.

새 상태를 읽을 수 있는 모든 Gateway를 먼저 배포한 뒤 재검토 기능을 켠다. 새 필드가 없는 기존 요청의 동작과 신형 오버레이가 오래된 Gateway에 연결될 때의 안내도 명시한다. 기능별 사용 가능 여부는 context 응답에 표시하고, 지원하지 않는 동작의 버튼은 제공하지 않는다. 기능 플래그는 새 작업의 생성 여부를 제어하며 이미 저장된 상태를 읽지 못하게 만들어서는 안 된다.

되돌릴 때는 우선 새 기능의 진입·쓰기를 끄고 기존 데이터를 읽을 수 있는 호환 빌드를 사용한다. NEEDS_REVIEW 데이터가 존재하는 DB에 해당 상태를 모르는 옛 빌드를 그대로 되돌리지 않는다. 새 테이블이나 본문 데이터를 제거하는 파괴적 역마이그레이션은 기본 복구 수단으로 삼지 않는다. 기존 공유 kill switch가 켜진 경우에는 앱 연결과 새 리뷰 쓰기를 막고 인증된 Control 리뷰함은 읽기 전용으로 제공하는 것을 1차 제안으로 고정한다. 관리자 계정·복구 작업은 기존 운영 경로를 유지한다. 운영 문서와 Control·Content 테스트에 이 동작을 함께 반영한다.

**검증은 사용자가 수행하는 작업을 중심으로 만든다.** 이번 계획에서 새로 실행한 제품 테스트는 없다. 아래는 구현 완료 시 수행할 검사와 목표이며 통과 결과가 아니다.

각 묶음은 관련 테스트로 먼저 확인한다. 공유 배포 후보에서는 `npm run check:mvp`와 실제 `TEST_DATABASE_URL`을 설정한 `npm run test:postgres`를 수행한다. Control 정적 자산과 의존성이 바뀌면 운영 이미지의 빌드·파일 포함·진입점 검사를 포함한다. DB 테스트를 환경 미설정으로 건너뛴 결과는 DB 검증 완료로 계산하지 않는다. 공개 배포 후보는 기존 공개 HTTPS 검증 절차에 리뷰함·댓글 링크·로그인 복귀를 추가해 별도로 확인한다.

파일럿 부하 목표는 계정 8개, 열린 브라우저 탭 16개, 프로젝트 3개, revision별 스레드 2,000개와 일부 스레드 답글 200개다. 현재 저장소와 배포 자원에서 목록 API p95 500ms 이내, 변경 후 다른 창 반영 p95 2초 이내를 잠정 목표로 삼는다. 환경·DB RTT·데이터 규모와 함께 측정하고 미달하면 조회 계획, 잠금 대기, 반복 재조회부터 조사한다. 이 값은 현재 성능 측정치나 제품 보장이 아니다.

브라우저 본문·앱 DOM·스크린샷을 추가 수집하지 않고 API 지연·실패 코드·이벤트 지연·재연결 횟수 같은 수치로 운영 상태를 확인한다. 검토 소요 시간과 발견 실패는 파일럿 참여자가 수행하는 정해진 작업에서 관찰 기록으로 남긴다. 사용자별 행동 추적 기능을 새로 만들 필요는 없다.

**파일럿은 한 팀의 실제 수정 작업 2회 이상으로 진행한다.** 개발자 1–2명과 검토자 2–3명을 모집한다는 가정으로, 서로 다른 두 페이지에 피드백을 남기고 개발자가 수정·재검토를 요청하는 흐름을 반복한다. 운영 배포와 계정 초대는 이 계획서 작성으로 실행된 것이 아니다.

| --- | --- |

| 다른 페이지의 피드백 발견 | `/cart`를 보던 사용자가 `/products`의 답글을 알림에서 찾아 30초 안에 해당 대화로 이동 |
| 영구 링크의 재사용 | 터널 종료 후 기록 열람, 같은 revision 새 터널 시작 후 앱 이동 성공 |
| 재검토의 완결 | 작성자가 요청을 찾아 확인 완료 또는 보완 요청까지 혼자 수행 |
| 앱 사용 방해 감소 | 패널을 접은 채 클릭·스크롤·폼 입력, 모바일 지점 핀 작성에 장애 없음 |
| 운영 상태 확인 | 잠정 지연 목표를 측정하고 DB 오류·권한 회수·재연결 시의 화면 안내를 확인 |

시간 목표는 파일럿을 비교하기 위한 잠정 기준이다. 첫 회차에서 기준 작업 시간을 함께 기록해 개선 전후를 비교한다. 사용자가 막히는 지점이 나오면 패널 문구·기본 필터·알림 진입을 먼저 조정하고, 기능 추가 여부는 두 번째 회차에서 판단한다.

내부 파일럿 이후 우선순위를 바꿀 조건도 정해 둔다. 버전 전환 때 같은 피드백을 반복 작성하면 선택적 버전 승계를 올린다. 상태·페이지 필터로도 항목을 찾기 어렵다면 검색을 올린다. 앱을 닫아 두어 내부 알림을 놓치는 일이 반복되면 외부 알림을 검토한다. 외부 검토자나 비공개 프로젝트가 필요하면 프로젝트 접근 목록을 다른 확장보다 먼저 진행한다.

이 계획에서 사용자 확인으로 확정된 것은 소규모 내부 팀을 우선한다는 점이다. 전체 팀 열람 범위 유지, 단계별 출시, 내부 알림 우선, 메모리 초안, 프로젝트별 권한과 버전 승계의 후속 분리는 이를 바탕으로 한 제안 기본값이다. 구현 전에는 현재 진행 중인 핀 변경을 기준선으로 확정하고 단계 A·B의 재현 테스트부터 시작할 수 있다.
