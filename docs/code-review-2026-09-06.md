# 전체 코드 리뷰와 개선 결과 — 2026-09-06

프로젝트에는 인증, 연결 복구, 전송량 제한, DB 저장, 운영 중지 기능과 테스트가 갖춰져 있다. 다만 **여러 일이 거의 동시에 일어나는 상황**과 **실제 브라우저의 로그인 과정**에서 문제가 확인됐다. 이번에는 재현 가능한 오류를 수정하고, 같은 상황을 자동으로 검사하는 테스트를 추가했다.

## 프로젝트가 하는 일

개발자 PC에서 실행 중인 웹사이트를 다른 사람이 로그인해서 볼 수 있게 하는 프로그램이다.

| 구성 | 쉬운 설명 | 담당 코드 |
| --- | --- | --- |
| Client | 개발자 PC의 웹사이트를 공유 서버에 연결한다. | `apps/client` |
| Gateway | 방문자의 로그인과 접근 권한을 확인하고 요청과 응답을 전달한다. | `apps/gateway` |
| 인증·DB | 계정, 로그인 상태, 권한 변경과 운영 설정을 저장한다. | `packages/auth`, `packages/storage-postgres`, `packages/operations` |
| 통신 규칙·중계 | 데이터의 형식, 연결 상태와 한 번에 보낼 수 있는 양을 관리한다. | `packages/protocol`, `packages/proxy`, `packages/relay` |
| 관리자 도구·운영 스크립트 | 계정 관리, 공유 허용, 점검, 백업과 복구를 담당한다. | `apps/admin-cli`, `scripts` |

통신 규칙과 인증 로직이 별도 패키지로 나뉜 점, 오래된 권한으로 접근하지 못하도록 권한 버전을 확인하는 점, 전송량과 대기 작업 수에 상한을 둔 점은 유지할 만한 구조다. 반면 Gateway와 Client의 핵심 파일에는 아직 여러 역할이 모여 있어 작은 수정의 영향 범위를 판단하기 어렵다.

## 확인하고 수정한 문제

P1은 서버 전체나 로그인·접근 제어에 영향을 주는 문제, P2는 특정 전송 상황에서 발생하는 문제를 뜻한다.

| 우선순위 | 기존 문제와 영향 | 수정 결과 |
| --- | --- | --- |
| P1 | 잘못된 WebSocket 연결 주소 하나가 처리되지 않은 오류를 일으켜 Gateway 전체를 종료할 수 있었다. | 주소 해석 실패를 잡아 해당 요청만 400 오류로 거부한다. 기존 공유는 계속 작동한다. |
| P1 | 공유 중지 시 이미 연결이 끊긴 세션은 정리되지 않아, 중지를 해제한 뒤 예전 연결을 되살릴 수 있었다. | 연결 생성 중·재연결 대기 중·재연결 검사 중에도 세션과 대기 작업을 즉시 정리한다. 종료한 세션의 재사용도 거부한다. |
| P1 | 사용하지 않던 DB 연결이 끊기면 처리되지 않은 오류로 Gateway가 종료될 수 있었다. | DB 연결 오류를 처리하고 공유 허용 상태를 일단 닫는다. 이후 DB에서 저장된 운영 상태를 다시 읽으면 그 상태에 따라 복구한다. |
| P1 | 브라우저의 출처 숨김 설정이 정상 로그인 폼의 출처까지 지웠고, 로그인 뒤 다른 호스트로 바로 이동하는 동작도 폼 보안 정책에 막혔다. | 정상 폼에는 같은 출처 정보를 유지한다. 로그인 성공 후 짧은 이동 페이지를 거쳐 공유 화면으로 돌아간다. 출처 검사와 폼 전송 제한은 유지하며, 일회용 코드 교환에는 출처 숨김을 적용한다. |
| P2 | 일반 HTTP 응답이 전송 대기 중인데 업로드가 끝나면 응답을 너무 일찍 정리해 브라우저가 끝을 기다릴 수 있었다. | 상대가 ‘전송 끝’ 신호를 보낸 시점과 실제 응답 종료 처리를 마친 시점을 구분한다. |
| P2 | 실시간 연결인 WebSocket에서도 브라우저가 보내기를 끝내면 남은 응답 종료 처리가 생략될 수 있었다. | 대기 중인 데이터를 처리하고 소켓의 보내기를 끝낸 뒤 연결 정보를 정리한다. |

마지막 두 문제는 택배에 비유하면 **물건이 아직 출고 대기 중인데 주문을 배송 완료로 정리하던 상황**이다. 이제 실제 출고 처리를 마칠 때까지 주문 정보를 남긴다.

주요 수정 위치는 [Gateway 중계 서버](../apps/gateway/src/server.ts), [DB 연결을 여는 실행 코드](../apps/gateway/src/main.ts), [웹 인증 처리](../apps/gateway/src/web-auth.ts), [로그인 화면](../apps/gateway/src/web-auth-pages.ts)이다.

## 테스트와 코드 구조 개선

- 오류 재현 테스트를 추가했다. 잘못된 주소 뒤 정상 요청, 공유 중지 후 예전 연결 재사용, 전송 대기 중 종료·취소, 실제 DB 연결 강제 종료를 검사한다.
- Vite·Next.js 브라우저 테스트를 실제 인증 과정으로 바꿨다. 개발자 로그인과 공유 생성, 검토자 로그인, 호스트별 로그인 쿠키, 화면 자동 갱신, 열린 WebSocket 종료와 접근 권한 회수를 확인한다. Next.js에서는 임시 비밀번호 변경도 거친다.
- 컴퓨터가 바쁠 때 간헐적으로 실패하던 시간 관련 테스트 2개는 테스트가 직접 시계를 움직이도록 바꿨다. 예를 들어 100ms 제한 중 앞 단계에서 75ms를 썼다면 뒷 단계에는 25ms만 남는지 정확히 검사한다.
- Client의 로컬 주소 검사와 연결 확인을 [local-origin.ts](../apps/client/src/local-origin.ts), WebSocket 응답 검사를 [websocket-upgrade.ts](../apps/client/src/websocket-upgrade.ts)로 분리했다. 외부에서 호출하는 기존 기능은 유지했다.
- Gateway의 공유 중지·권한 회수·만료·명시적 종료에 필요한 정리를 공통 처리로 모았다. 종료 이유마다 정리 방식이 달라져 생기는 누락을 줄였다.

## 확인한 결과와 범위

Node.js 24.12.0과 로컬 Chrome에서 `npm run check:mvp`를 통과했다.

| 검사 | 결과 |
| --- | --- |
| TypeScript 타입 검사·패키지 의존 경계·빌드 | 통과 |
| 운영·배포·백업 등을 검사하는 스크립트 테스트 | 48개 통과 |
| 단위·통합 테스트, 실제 PostgreSQL 연결 포함 | 285개 통과, 실패·건너뜀 0개 |
| Vite·Next.js 실제 브라우저 테스트 | 2개 통과 |
| CI와 같은 PostgreSQL 17.6의 별도 DB 테스트 | 8개 통과 |

전체 검사는 격리된 PostgreSQL 15에서 수행했고, CI와 같은 digest로 고정된 PostgreSQL 17.6 이미지에서도 DB 테스트 8개를 모두 통과했다. 세부 결과는 [구현 상태 문서](poc-status.md)에 기록했다. 위 브라우저 검증은 로컬 HTTP에서 개발용 쿠키를 사용했다.

이후 같은 날 실제 Ubuntu 서버에 Gateway 운영 이미지를 빌드·배포하고 실제 DNS·HTTPS 경로도 검증했다. public-path canary와 공유 허용 승인, Vite·Next.js의 실제 로그인·기능·권한 회수, 재시작 후 저장 상태 유지가 통과했다. 전체 역할별 Docker 이미지 빌드와 장기 운영 인수는 남아 있다. 공개 가능한 환경·검사 결과는 [익명 HTTPS 검증 보고서](validation/public-https-2026-09-06.md), 재실행 방법은 [외부 경로 검사 안내](public-path-testing.md)를 참고한다.
