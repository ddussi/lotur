# 로그인 화면 개선 계획

2026-09-08. 대상은 관리자에게 계정을 받은 소규모 내부 팀이다. 이번 문서는 계획이며, 로그인 화면 구현은 아직 변경하지 않았다.

**목표는 처음 방문한 사람이 로그인 방법을 바로 알고, 실패해도 쉽게 다시 시도하고, 보려던 리뷰까지 도착하는 것이다.**

## 현재 코드에서 확인한 점

- `apps/gateway/src/web-auth-pages.ts`의 로그인은 공통 페이지 안에 설명·입력창·버튼만 배치한다. 로그인과 넓은 관리자 표가 같은 기본 스타일을 사용한다.
- 아이디·비밀번호의 label과 브라우저 자동완성은 이미 있다. 이를 유지하고 입력 너비·간격·초점 표시를 개선한다.
- 비밀번호 표시 전환, 전송 중 상태, 실패 후 아이디 유지가 없다.
- 오류는 일반 문단으로 표시된다. 일부 일시적 장애는 폼 대신 안내 페이지만 표시해 다시 시도하기 어렵다.
- 임시 비밀번호를 받은 사람은 로그인 뒤 비밀번호 변경 화면을 통과한다. 두 화면을 하나의 가입 완료 과정처럼 이어 주어야 한다.
- `returnTo`로 리뷰함 댓글에 돌아가는 기능은 구현되어 있다. 한편 공유 앱 로그인용 `intent`는 폼의 숨긴 필드로 전송하지만 오류 처리에서는 URL에서 다시 읽는다. 잘못된 비밀번호 후 재시도할 때 공유 앱으로 돌아갈 정보가 사라지는지 회귀 테스트로 먼저 확인한다. 비밀번호 변경 실패도 같은 조건으로 확인한다.

## 화면 구성

**웜 화이트 배경 + 차콜 글자 + 짙은 버건디 버튼**으로 정한다. 흰 바탕에서 읽고 입력하는 데 집중하고, 가장 중요한 행동에만 색을 쓴다. 외부 폰트·이미지나 새로운 UI 프레임워크는 필요하지 않다.

정한 색상으로 계산한 대비는 흰 버튼 글자와 버건디 배경 약 8.76:1, 본문과 화면 배경 약 14.32:1, 보조 글자와 화면 배경 약 5.50:1이다. 실제 렌더링에서도 오류·초점·버튼 상태를 다시 확인한다. 오류는 문장과 위치로도 구별해 색만 보고 판단할 필요가 없게 한다.

- 떠 있는 큰 카드 대신 최대 너비 400px의 입력 영역을 화면 중앙에 둔다. 제품명·제목·항목 이름·입력 내용은 왼쪽 정렬한다.
- 화면의 색 대부분은 웜 화이트와 차콜이 차지한다. 버건디는 기본 버튼과 초점 표시에 집중한다.
- 입력창과 버튼의 모서리는 6px, 테두리는 1px로 한다. 큰 둥근 모서리, 그림자, 광택, 그라데이션, 장식용 그림은 사용하지 않는다.
- 시스템 글꼴을 사용한다. 제목 28px, 입력 글자 16px, 설명·도움말 14px를 기준으로 한다. 입력 항목 사이 20px, 제목 묶음과 폼 사이 28px, 폼과 도움말 사이 24px를 둔다.
- 첫 적용은 이 밝은 화면을 기준으로 한다. 대화 속 시안은 호스트의 어두운 모드에도 대응하지만, 제품의 다크 모드 제공은 이번 구현의 필수 범위에 추가하지 않는다.

| 제품 이름 | Review Tunnel | 어느 서비스인지 확인 |

로그인 전에 프로젝트 이름이나 댓글 내용을 표시하지 않는다. 별도 관리자 연락처가 설정되어 있지 않으므로 존재하지 않는 문의 링크는 만들지 않는다.

데스크톱은 최대 너비 400px의 입력 영역으로 모은다. 모바일은 좌우 24px 여백과 한 열 배치를 사용한다. 화면 높이를 고정하지 않아 키보드가 올라오거나 오류 문장이 늘어나도 페이지를 스크롤할 수 있게 한다. 입력창·주요 버튼 높이는 48px을 기준으로 하고, 비밀번호 표시 전환도 누르기 쉬운 크기를 확보한다.

아이디 오류와 비밀번호 오류를 따로 구별해 계정 존재 여부를 노출하지 않는다. 비밀번호를 HTML 응답·브라우저 저장소에 다시 넣지 않는다. 기존 인증 판단과 재시도 제한은 서버가 담당한다.

## 함께 개선할 비밀번호 변경 화면

- 로그인과 같은 간격·색·입력창·오류 위치를 사용한다.
- 현재 비밀번호, 새 비밀번호, 새 비밀번호 확인의 label을 명확히 구분한다.
- 현재 서버의 길이 등 비밀번호 규칙을 입력 전부터 설명한다. 화면에만 별도의 규칙을 만들지 않는다.
- 새 비밀번호 확인이 다르면 해당 칸 아래에 설명한다. 서버 오류도 같은 위치 체계로 표시한다.
- 각 비밀번호 표시 전환과 `current-password`·`new-password` 자동완성을 지원한다.
- 변경 실패 후에도 원래 리뷰로 돌아갈 정보를 유지한다. 변경에 성공해야 리뷰로 이동한다.

## 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 실패·복귀 동작 확인 | 잘못된 비밀번호 → 재시도 → 원래 공유 앱·리뷰 댓글 복귀를 테스트로 재현 |
| 2 | 로그인 전용 화면 틀과 정적 스타일 | 모바일·데스크톱에서 읽기 좋은 배치. 관리자 표의 너비와 배치에 영향 없음 |
| 3 | 입력과 오류 개선 | 아이디 유지, 비밀번호 표시, 전송 상태, 오류 이후 다시 시도 가능 |
| 4 | 비밀번호 변경 화면 연결 | 임시 계정도 변경 실패·재시도를 거쳐 원래 리뷰에 도착 |
| 5 | 접근성·브라우저·시각 확인 | 키보드만으로 완료하고, 오류를 읽을 수 있고, 작은 화면에서 가로 스크롤 없음 |

주요 수정 대상은 `web-auth-pages.ts`, `web-auth.ts`와 작은 인증 화면 보조 스크립트다. 로그인 전용 레이아웃을 두어 관리자·계정 관리 화면의 공통 스타일을 무조건 바꾸지 않는다. 페이지 렌더링은 문자열 인자 추가보다 입력값·오류·이동 문맥을 구분한 데이터 객체로 정리한다.

기본 로그인은 기존 HTML 폼 제출로 작동하게 한다. 비밀번호 표시·전송 중 상태만 작은 스크립트로 보완하고, 스크립트를 사용할 수 없어도 로그인·비밀번호 변경이 가능해야 한다. 현재 인증 화면은 스크립트를 차단하므로 필요한 로그인·비밀번호 변경 응답에만 서버가 생성한 nonce로 보조 스크립트를 허용한다. 전체 인증 페이지의 스크립트 제한을 일괄 해제하지 않는다.

오류가 발생한 요청에서 아이디와 복귀 정보를 유지할 수 있도록 요청 단위의 제한된 화면 상태를 보관한다. 공유 앱 `intent`와 리뷰함 `returnTo`는 용도를 구분하고, 기존 검증·만료·인증 경계를 통과시킨다. 비밀번호는 화면 상태 객체에 포함하지 않는다.

## 검증 계획

정적인 색·간격마다 단위 테스트를 추가하지 않는다. 실제 실패·입력·이동 동작에 테스트를 집중한다.

1. 정상 로그인과 임시 비밀번호 변경 후 원래 리뷰·공유 앱으로 돌아간다.
2. 잘못된 비밀번호를 한 번 입력한 뒤 성공해도 목적지가 유지된다. 실패 후 아이디는 남고 비밀번호는 비어 있다.
3. 비밀번호 확인 불일치·서버 거부 후 다시 제출해도 목적지가 유지된다.
4. 표시 전환이 글자를 바꾸지 않으며 자동완성과 붙여넣기를 막지 않는다.
5. Tab·Shift+Tab·Enter로 사용할 수 있다. 표시 전환 버튼도 키보드로 작동한다. 오류는 색과 함께 글로 설명하며 읽기 보조 프로그램에 전달한다.
6. 느린 응답에서 중복 제출을 막고, 실패·뒤로 가기 후 버튼이 계속 잠긴 상태로 남지 않는다.
7. 스크립트를 끈 상태에서도 로그인과 비밀번호 변경이 가능하다.
8. 360px·390px·768px·1440px 화면과 확대 상태에서 입력·오류·도움말을 확인한다. 긴 한국어 오류 메시지, 포커스 표시, 밝기 대비도 확인한다.
9. 기존 계정·관리자 화면, 인증 경계, Vite·Next.js 공유 로그인과 리뷰함 영구 링크 테스트를 통과한다.

화면 초안은 기본·오류·전송 중·임시 비밀번호 변경 상태를 캡처해 확인한다. 마지막에는 관련 인증 테스트와 `npm run check:mvp`를 수행한다.

## 범위와 예상 작업량

우선 적용할 범위는 로그인과 필수 비밀번호 변경이다. 회원가입, 이메일 재설정, 소셜 로그인, 새 계정 정책은 별도 기능으로 두고 이번 로그인 화면 계획에 추가하지 않는다.

인증 실패 후 복귀 문제 확인부터 화면·상태 구현·브라우저 검증까지 **약 2–3 개발일**을 초기 작업량으로 잡는다. 기존 복귀·인증 오류 처리에 추가 문제가 확인되면 그 부분의 영향과 일정을 다시 산정한다. 실제 소요 시간을 측정한 값이나 납기 약속은 아니다.
